# Core Website — Full Build Report

Live site: `https://site-creator-vinext-starter.bankerrunners.workers.dev/portal-rebuild-Mr.T-CORE-JARVIS`

## Executive summary

Core has been built as a distinct agency operating-system concept — not a copy of Epic Life, The Standard HQ, or Jarvis.

The central idea is:

> Core does not sell lists of names. It creates, verifies, routes, and learns from in-house demand.

The current website connects six major operating layers:

1. In-house lead monetization
2. Agent ranking and compensation
3. Carrier intelligence
4. Daily command and prioritization
5. Call analysis and coaching
6. Evidence-backed scripts

The experience is fully deployed, responsive, interactive, and production-tested. It is currently secured to the owner account.

## 1. Core's strategic difference

The competing systems are largely dashboards: they display production, policies, rankings, calls, scripts, and AI chat.

Core is designed around a closed intelligence loop:

```text
Signal → Call → Carrier → Policy → Retention → Better signal
```

Information should not remain trapped in separate tools. A call should influence coaching. Coaching should improve scripts. Policy outcomes should improve carrier routing. Retention should affect agent rank and lead quality.

Core's advantage is the connection between those activities.

## 2. The in-house Signal Exchange

The lead-vendor model is presented as a verified signal exchange.

Partners fund a defined operating lane based on:

- Licensed geography
- Availability and capacity
- Intended opportunity volume
- Contact permissions
- Qualification requirements
- Routing fit

A Core Verified Signal contains:

- Traceable source
- Appropriate contact permission
- Documented customer need
- Qualification context
- Routing justification
- Accountable disposition

The site includes an interactive capacity model where monthly opportunity volume and funding per signal can be adjusted. It demonstrates:

- Total funded capacity
- Amount released after verification
- A visible 15% quality reserve

The reserve is an illustrative commercial concept for handling duplicates, invalid records, out-of-scope opportunities, delivery disputes, and replacements.

Payment is tied to a documented opportunity standard — not an insurance purchase, policy placement, or commission outcome.

## 4. CarrierOS

CarrierOS consolidates carrier knowledge into a single operating workspace.

The prototype includes:

- Carrier library
- Product tiers
- Issue ages
- Face-amount ranges
- Benefit classifications
- Underwriting search
- Build guidance
- Riders
- Support escalation
- Internal fit score

The Royal Neighbors experience was used as a reference case, but Core's structure is broader and designed to connect carrier guidance with actual customer and call context.

A built-in underwriting search demonstrates topics such as COPD and respiratory history, diabetes, cancer history, stroke and TIA, and oxygen use.

The system deliberately avoids representing planning guidance as guaranteed underwriting approval. Current carrier materials, state availability, licensed-agent review, and actual underwriting decisions remain controlling.

## 5. Core Command

Core Command replaces a generic AI-chat model with a ranked mission queue.

It contains four working views:

- Today
- Book
- Coach
- Growth

Examples of ranked actions include:

- Recovering pending requirements
- Re-routing leads after licensing or carrier changes
- Protecting policies showing retention risk
- Reviewing a winning objection path
- Refreshing a script supported by sold calls
- Unblocking carrier appointments
- Advancing agents who are near the next rank

Priorities are organized by urgency and durable value. The intention is to show the operator what deserves attention without requiring them to know what to ask an AI assistant.

## 6. Goal Engine

The interactive Goal Engine translates an annual planning target into:

- Monthly target
- Weekly target
- Estimated placed policies
- Required daily quality conversations

The user can adjust annual production from $100,000 to $1 million.

These results are illustrative. Actual results depend on editable assumptions such as average placed premium, contact rate, close rate, placement rate, persistence, lead quality, and agent capacity. It is not presented as an income promise.

## 7. Call Lab

Call Lab was designed after reviewing the inbound-call library, individual call analyses, transcripts, objections, key moments, talk balance, outcomes, and coaching markers.

Instead of functioning as a transcript archive, it converts calls into portfolio intelligence.

The prototype supports:

- All inbound calls
- Won calls
- Lost calls
- Calls needing review
- Call scores
- Trust scoring
- Discovery scoring
- Decision-clarity scoring
- Compliance scoring
- Decision timelines
- Portfolio patterns
- Ranked coaching actions

The underlying philosophy is:

> Do not replay the entire hour. Identify the five minutes that changed the outcome.

Call Lab also separates service quality from sales results. For example, a sensitive death-claim call should not be considered unsuccessful simply because it did not result in a sale.

## 8. Nate's call review

The reviewed record was a 1:03:41 inbound call beginning with an unexplained $723.10 charge.

The source platform identifies the agent as Jake Chattinger. Because these were referred to as Nate's calls, Core presents the review under the generic record `N-001` rather than asserting an identity that the source did not verify.

Core score: 79/100

Category scores:

- Trust: 91
- Discovery: 93
- Decision clarity: 72
- Compliance: 76

What went well:

- Strong emotional control at the beginning.
- Acknowledged the $723 concern and validated the caller's frustration.
- Widened the conversation from billing inquiry toward a policy review.
- Began inventorying existing coverage.
- Entered detailed health discovery.
- Identified a possible waiting-period issue.
- Summarized the loan and coverage concerns.
- Attempted to recover from the dropped connection with a callback.

What could improve:

- Keep the original billing problem distinct while expanding into a policy review.
- Ask explicit permission before moving from service issue to coverage review.
- Compress repetitive discovery.
- Verify carrier and policy details before stating conclusions.
- Avoid presenting estimated waiting-period, policy-loan, or carrier information as confirmed.
- Introduce the decision framework earlier.
- Secure an exact callback number, time window, purpose, and owner.
- Confirm consent and privacy requirements before using a direct line or follow-up channel.

Recommended coaching assignment:

1. Rebuild the 03:31 service-to-review transition.
2. Rebuild the 29:36 policy-gap explanation.
3. Rebuild the 62:47 callback commitment.

The objective is not to reduce discovery. It is to make discovery feel authorized, structured, and connected to a clear next decision.

## 9. Script Vault

The Script Vault contains original, illustrative Core plays:

- Service to Review
- Gap Before Option
- One-Book Review
- Callback Recovery

Each play contains:

- Intended inbound situation
- Evidence for when it should be used
- Four structured stages
- Compliance guardrail
- Outcome-linked promotion logic

Scripts are treated as living operational assets. A phrase should only become an approved play after it is supported by won-versus-lost evidence, manager review, compliance review, and downstream policy outcomes.

This preserves agent personality while eliminating improvisation around high-risk facts.

## 10. Security and personal logins

The live site is currently configured with custom restricted access.

Current owner: `core_inbox_pm@pm.me`

Each company member can have their own authenticated access. Passwords should not be stored in the website, source code, spreadsheets, or a shared agency database.

Secure access should be handled by the identity provider so that:

- Every employee has an individual identity
- Sessions can remain signed in on trusted devices
- Access can be revoked per person
- Password resets stay outside Core
- Activity can eventually be attributed to the correct user
- Former employees can be removed without changing everyone's password

The current Sites workspace supports custom invitations or public access. It does not currently expose an automatic "everyone in this company domain" option for this project. Company-wide secure access therefore requires the employee email roster.
